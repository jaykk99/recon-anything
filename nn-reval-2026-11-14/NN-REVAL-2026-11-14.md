## Question

The hypergraph winner (`feat/nn-hypergraph` @ 622dbee, reported acc 0.9514)
and the multimodal winner (`feat/nn-multimodal` @ 3b4507a, reported acc 0.9724)
were measured on a holdout that shifted 145 -> 144 rows mid-batch (a
findings dedupe rewrote `candidates.jsonl`), so neither number was directly
comparable to shipped v2 (acc 0.9103 on the fixed 145-row holdout).
This re-validation retrains all three models on the exact same 145 test rows
and settles whether they really beat v2.

## Correction to the task premise (multimodal)

The multimodal branch's committed numbers were ALREADY on the fixed
145-row holdout: its doc (`backend/docs/nn-multimodal.md`) records a first
run on the 144-row holdout (MLP acc 0.9444) and a rerun against the Nov 12
backup that produced the shipped 0.9724. This re-validation is therefore an
independent reproduction of that rerun, not a first fix. It reproduces
0.9724 exactly (see below).

## Checkpoint patch (worktree-only, trajectory-neutral)

The multi/hyper branches' `mlp.py` / `hypergraph.py` have no checkpoint
support (v2's does). The worktree copies were patched to write weights to
disk every 20 epochs (atomic tmp + rename) at epoch end — a pure
side-effect write that touches no weights, no RNG state, no training order.
Patches saved in `patches/` (diffs vs the branch heads). Fidelity proof:
the patched multimodal run reproduces the branch's committed numbers
bit-for-bit (every metric below identical to `viewer-data.json` on
`feat/nn-multimodal`), and the patched v2 run reproduces the sweep record
exactly. `train_v2_ownholdout.py` already checkpointed every 20 epochs;
the only change for the reval copy (`scripts/train_v2_ownholdout_reval.py`)
is the candidates path pointing at the backup.

Incident log: a VM reboot mid-run wiped `/tmp` (first chain: v2 + multimodal
done, hypergraph killed in its baseline phase). Everything was relaunched
from persistent workspace paths (`scripts/run_reval.sh`); the pre-reboot
v2/multimodal numbers were reproduced exactly by the relaunch, and the
relaunch is the run of record below. No results below come from the
pre-reboot run.

v2 recomputation: acc and confusion identical to the sweep record
(0.9103, tp114 fp3 fn10 tn18); AUC 0.9685 vs recorded 0.9697, the known
sparse-forward 1-ULP drift documented in the sweep record. Baseline 0.8552.

Hypergraph, same run: no-edge ablation acc 0.9241 / AUC 0.9666 (edges add
+1.4 pts acc, +0.016 AUC). Same-split 60-epoch MLP baseline acc 0.9103 /
AUC 0.9731, confusion identical to the 120-epoch v2 (tp114 fp3 fn10 tn18).
Hypergraph coverage: 11 edges, 31/145 test nodes covered (~21%);
covered-slice acc 0.9032 (n=31) vs singleton acc 0.9474 (n=114) — the
covered rows are the harder slice; the gain shows in the ablation, not in
the slice split. Train 70 edges, 276/2,502 nodes covered.

Multimodal, same run: k-NN-only acc 0.9241 / AUC 0.9731 (tp119 fp6 fn5
tn15); blend 0.7 MLP + 0.3 kNN acc 0.9655 / AUC 0.9881 (tp121 fp2 fn3 tn19);
retrieval P@5 0.9283, macro 0.7004, excl-dominant 0.7920. Permutation
importance: multimodal_embeddings 3rd (AUC drop 0.0215, behind
bounty_value 0.1974 and contract_role 0.0741). Modality coverage:
bytecode **0.0% on train and test** — the gain is source + finding
embeddings only; bytecode taught the model nothing on this data.

## Verdicts

- **Multimodal: HONESTLY BEATS v2.** +6.2 pts accuracy (0.9724 vs 0.9103,
  9 rows), +0.0165 AUC (0.9850 vs 0.9685), FP recall 0.905 vs 0.857,
  WV recall 0.984 vs 0.919. The reported 0.9724 was already on the fixed
  holdout and reproduces exactly. No cherry-picking: same 145 rows, same
  metrics, same protocol. Caveats: train acc 0.9952 vs test 0.9724 is a
  memorisation gap (not extreme, and the kNN/blend/retrieval checks agree
  the signal is real); bytecode modality is empty, so the "multimodal"
  label overstates what was measured — it is source + finding embeddings.
- **Hypergraph: HONESTLY BEATS v2, by less than reported.** +2.8 pts
  accuracy (0.9379 vs 0.9103, 4 rows), +0.0138 AUC (0.9823 vs 0.9685),
  FP recall 0.905 vs 0.857, WV recall 0.944 vs 0.919. The reported 0.9514
  was inflated by the holdout shift: on the 144-row test the model had
  fn=2 / fp=5 (WV recall 0.984, FP recall 0.762); on the fixed 145-row
  test it is fn=7 / fp=2. The 144-row draw was easier for this model and
  harder for the MLP baseline (same-split baseline: 0.8889 on 144 rows vs
  0.9103 on 145). The gain on the fixed holdout is real — the no-edge
  ablation confirms the edges carry signal — but the honest margin is
  +2.8 pts, not the reported +4.1. Caveat: train acc 0.9892 vs test
  0.9379 (5.1-pt gap); the covered-slice split above.
- **Neither model hits 100% anywhere.** No overfit-flag win claimed.

## How to reproduce

```bash
# from the repo root, worktrees off origin/master:
git worktree add ~/workspace/wt/nn-reval-v2 origin/feat/nn-scorer
git worktree add ~/workspace/wt/nn-reval-multi origin/feat/nn-multimodal
git worktree add ~/workspace/wt/nn-reval-hyper origin/feat/nn-hypergraph
# apply patches/*.patch to the multi/hyper worktrees (checkpointing only)
bash nn-reval-2026-11-14/scripts/run_reval.sh   # detached via nohup
```

Exact commands per model (all use the backup candidates file):

- v2: `python3 -m app.nn.train_v2_ownholdout_reval`
  (in the nn-scorer worktree `backend/`, 255-64-32-1, 120 ep, lr 0.05)
- multimodal: `python3 -m app.nn.train --candidates <backup> --batches
  <batches.jsonl> --external app/nn/external_findings.jsonl --holdout own
  --hidden 64,32 --epochs 120 --multimodal`
- hypergraph: `python3 -m app.nn.train_hypergraph --candidates <backup>
  --batches <batches.jsonl>` (200 ep, hidden 16, lr 0.5 step-decay
  30/70/100, plus the 60-epoch MLP baseline in the same run)
